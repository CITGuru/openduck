One ATTACH. One JOIN. The DuckDB optimizer plans across both sides; only the intermediate results cross the wire.

The challenge

DuckDB is brilliant — and brilliantly local.

Storage

One process owns the file

The .duckdb file is a single mutable artifact. Multiple writers? Not really. Read-after-write consistency across machines? You're on your own.

Catalog

Catalog is in-process

Tables, schemas, types — all live inside the running DuckDB instance. There's no network catalog you can attach to.

Execution

Compute can't roam

Push a query into the cloud where the data is, get results back? Not without a protocol that DuckDB doesn't ship.

The opportunity

DuckDB's extension API is real

StorageExtension + Catalog let us pretend to be a normal database — and do anything we want under the hood.

Why this exists

DuckDB is local.
Your data, your team, your workloads aren't always.

1 · Data outgrew the laptop

Production data isn't on your machine

It's in S3, in a warehouse, in another cloud, in a partner system. Round-tripping it to a local .duckdb file to query is slow, wasteful, and frequently impossible.

2 · Teams can't share a file

One file, one writer

A .duckdb file isn't safe for concurrent writers. There's no shared snapshot, no read-after-write across processes, no time travel. Collaboration falls back to ad-hoc copies.

3 · The best query is hybrid

Small here, big there

Dimensions, lookups, dev data — fastest on your laptop. Fact tables, event logs, snapshots — best where they live. You want one query that uses both, planned by one optimizer.

A remote, snapshotted, dual-execution DuckDB exists because a thin REST wrapper around SELECT doesn't solve any of these. You need a real catalog, a real plan splitter, and storage that handles multiple readers safely.

Where the ideas come from

MotherDuck pioneered the ideas.
OpenDuck makes them open.

The inspiration

MotherDuck showed DuckDB can work beautifully in the cloud — md:mydb, transparent attach, queries split between laptop and cloud, snapshot-based storage.

The gap

It's a closed commercial service. The protocol is private, the backend is theirs, and the extension is bundled into DuckDB.

OpenDuck

An open re-implementation: open gRPC + Arrow protocol, swappable backend, separate loadable extension you can build & modify.

Not wire-compatible with MotherDuck — same architectural shape, MIT-licensed implementation.

System architecture

From ATTACH to bytes — the whole picture

Pillar 1 · Differential storage

Append-only sealed layers.
One serialized writer. Many concurrent readers.

Layers

Every write becomes a sealed, immutable file in object storage. Layers are content-addressable and never rewritten.

Snapshots

A snapshot is a manifest in Postgres — a list of layer IDs. Read at any snapshot to get a consistent view. Time travel comes for free.

Concurrency

Readers never block. A new writer creates a new snapshot; old readers continue against their own. No locks on hot paths.

Pillar 1 · The differential part

Newer extents shadow older ones at the same address.

Layers don't just add data — they overlay it. A read walks extents newest-first; first match wins. That's why it's "differential", not just "append-only".

The read loop · diff-core/src/memory.rs
// newest extent at the same address wins
for e in inner.extents.iter().rev() {
    if offset < e.logical_start
       || offset >= e.logical_start + e.length
    { continue; }
    if let Some(ms) = max_sealed {
        if e.layer_index > ms
           || e.layer_index == ACTIVE
        { continue; }     // snapshot bound
    }
    return blob[e.phys_start + (offset - e.logical_start)];
}
Three rules to remember
  • Writes append — extents go into the active layer, never overwrite.
  • Reads scan newest-first — first matching extent wins.
  • Snapshots cap the search — bound the layer index, the past becomes immutable.
Pillar 2 · Hybrid (dual) execution

One query.
Two engines. No copy-and-paste.

The gateway splits the plan into LOCAL and REMOTE fragments, runs each on the right engine, and inserts Bridge operators at the boundary. Only intermediate Arrow batches cross the wire.

How the planner decides

Auto, hint, or build-side.

1 · Auto

Catalog tells the planner

Each Scan checks if the table is in the worker's remote_tables set. Other operators inherit placement from the majority of children.

// crates/exec-gateway/src/hybrid.rs
fn resolve_auto(node: &PlanNode) -> Placement {
    match node {
        Scan { table } => remote_tables
            .contains(table).then_some(Remote)
            .unwrap_or(Local),
        _ => majority_of_children(node),
    }
}
2 · Hint (mirrors md_run)

Force it with openduck_run

Wrap a fragment with an explicit placement. The planner respects the hint and routes accordingly.

-- ship the heavy bit to the worker
SELECT l.*
FROM local_t l
JOIN openduck_run('REMOTE',
   'SELECT * FROM big_remote_t') r
  ON l.id = r.id;
3 · Build-side

Small side wins

For hash joins the planner prefers the smaller input as the build side. Build placement biases the rest of the plan — small-local + big-remote becomes the default shape.

// chosen by row-count estimates
HashJoin
  ├─ [BUILD] Scan local.dim   // small
  └─ [PROBE] Scan remote.fact  // big
Pillar 3 · Open protocol

Four RPCs.
Arrow IPC does the heavy lifting.

Data plane · 2 RPCs
rpc ExecuteFragment(...)
   returns (stream ExecuteFragmentChunk);

rpc CancelExecution(...)
   returns (CancelReply);

A plan fragment in, a stream of ArrowIpcBatch out. Cancellation is a single fire-and-ack RPC routed by execution_id.

Control plane · 2 RPCs
rpc RegisterWorker(WorkerRegistration)
   returns (RegisterWorkerReply);

rpc Heartbeat(HeartbeatRequest)
   returns (HeartbeatReply);

Workers self-describe: databases, compute_context, max_concurrency. The gateway routes by affinity.

Transactions & ingest
rpc BeginTransaction(...)
rpc CommitTransaction(...)
rpc RollbackTransaction(...)

// client-streaming for bulk ingest
rpc IngestData(stream IngestChunk)
   returns (IngestReply);

A txn id pins all subsequent calls to the same worker connection. Ingest streams Arrow batches into a temp table the client can INSERT…SELECT from.

Why this is small

No GetTables, no schema RPCs, no SQL helpers. The DuckDB extension is the catalog client. The protocol just moves SQL one way and Arrow the other. ~220 lines of proto.

The DuckDB extension

Pretend to be a normal database.

Storage Extension

Owns the openduck: scheme

DuckDB calls our attach hook for any URL starting with openduck:. We parse the path, build a connection, return a Catalog.

Catalog

Mints schemas & tables on demand

OpenDuckCatalog hands back schemas; schemas hand back OpenDuckTableEntry; tables hand back a scan function that streams Arrow.

Optimizer

First-class catalog entries

Statistics, types, predicate pushdown — DuckDB sees them as it would a local table. Joins and CTEs work without any special syntax.

// extension entry — register the storage scheme
extern "C" void openduck_init(DatabaseInstance &db) {
  StorageExtension ext;
  ext.attach        = OpenDuckStorageAttach;     // openduck:mydb
  ext.create_transaction_manager = OpenDuckTxn;
  db.config.storage_extensions["openduck"] = ext;
  db.config.storage_extensions["od"]       = ext;  // short alias
}

// catalog returns a table entry the optimizer can plan against
unique_ptr<CatalogEntry>
OpenDuckSchemaEntry::GetEntry(CatalogTransaction tx, CatalogType, const string &name) {
  auto meta = client.DescribeTable(database_, name);     // gRPC
  return make_uniq<OpenDuckTableEntry>(*this, name, meta);
}

// the table's scan function opens an Arrow IPC stream
TableFunction OpenDuckTableEntry::GetScanFunction(...) {
  return TableFunction(
      "openduck_scan",
      arrow_scan_bind, arrow_scan_init, arrow_scan_next);
}
Worker affinity routing

The gateway picks the right worker — by hand, not by vibes.

Self-describing workers
WorkerRegistration {
  worker_id        = "w-7a3f"
  databases        = ["warehouse"]
  compute_context  = "region=us-east-1"
  max_concurrency  = 8
  tables           = [...]   // optional
}
Heartbeats keep it fresh

Every 5 seconds. Skip three, you're evicted. Re-register and you're back. Stateless workers scale horizontally without coordination.

Act 3 · Hybrid join

Local table × remote table — one query, two engines.

terminal · duckdb cli (continued)
D CREATE TABLE tagged_users AS
    SELECT * FROM (VALUES (1,'vip'),(2,'beta'),(3,'beta')) t(id, tag);

D EXPLAIN SELECT u.name, t.tag, count(e.id) AS n_events
  FROM cloud.users u
  JOIN tagged_users t   ON u.id = t.id
  JOIN cloud.events e  ON e.user_id = u.id
  GROUP BY u.name, t.tag;

┌──────────────────────────────────────────────────┐
│ Physical Plan                                    │
├──────────────────────────────────────────────────┤
│  HASH_GROUP_BY                             [L]   │
│   └─ HASH_JOIN  (u.id = t.id)              [L]   │
│       ├─ SEQ_SCAN  tagged_users            [L]   │
│       └─ BRIDGE  R→L · arrow stream        [L]   │
│           └─ REMOTE_SCAN  cloud.users      [R]   │
│               JOIN cloud.events ...              │
└──────────────────────────────────────────────────┘

-- only the small probe-side intermediate crosses the wire
Build side · LOCAL

Small tagged_users stays put. DuckDB hashes it on your laptop.

Probe side · REMOTE

The big join with cloud.events runs on the worker — close to the data.

Bridge

The aggregated probe stream crosses as Arrow IPC. The final group-by happens locally.

Act 4 · Snapshots & time travel

The same database. Two consistent views.

terminal · duckdb cli
D SELECT snapshot_id FROM openduck_current_snapshot('mydb');
  snap_3

D INSERT INTO cloud.events VALUES (gen_random_uuid(), 1, 'click', now());
D SELECT count(*) FROM cloud.events;
  912 348

D SELECT snapshot_id FROM openduck_current_snapshot('mydb');
  snap_4   -- new sealed layer, new snapshot

-- attach the same db at the OLD snapshot in a separate alias
D ATTACH 'openduck:mydb?snapshot=snap_3&token=dev-token' AS past;

D SELECT count(*) FROM past.events;
  912 347   -- one fewer — the row we just inserted is gone

D SELECT count(*) FROM cloud.events;
  912 348   -- live snapshot still sees it

Engineering choices

Use the right tool, not the favorite tool.

Rust · gateway, workers, bridge

Where most of the concurrency, networking, and failure modes live. tonic for gRPC, arrow-rs for IPC, tokio for everything async.

11 crates · ~25k lines · workspace-wide CI

C++ · DuckDB extension

Because that's the language of the StorageExtension API. A small libdiff_bridge.a static lib lets us reach into Rust for the metadata client.

vcpkg-based build · CMake · publishable to community-extensions

Arrow IPC · the wire

Self-describing schemas, columnar layout, every language has a reader. The protocol just moves blobs of IPC bytes; nothing else needs to know the schema.

~64 MiB max message · streaming · zero schema RPCs

Postgres · metadata

Snapshots, layer manifests, live ingest transactions. Free transactions, mature operational story, easy migration story with sqlx.

Embedded SQLite mode for dev · Postgres for prod

Object store · sealed data

Append-only, content-addressable, immutable. S3, R2, MinIO — anything that speaks the S3 API.

FUSE adapter (linux) for filesystem-style mounting

OpenTelemetry · observability

Optional OTLP exporter in openduck-metrics. Per-RPC latencies, worker queue depth, layer write rates.

Off by default · zero-cost when disabled

Lessons learned

Things I'd tell past-me.

Security · the hard lessons
  • RegisterWorker was unauthenticated — anyone reachable could intercept queries.
  • Arrow column names in hybrid CREATE TEMP TABLE DDL → SQL injection. Always quote_ident().
  • Hand-rolled constant-time compare was compiler-optimizable. Use the subtle crate.
  • Postgres URL was leaking via Debug. Custom impl that redacts.
  • Path traversal via storage_uri. Reject .. and absolute paths.
Architecture wins
  • Tiny protocol, fat extension. Catalog logic lives client-side.
  • Arrow IPC means no schema RPCs and no negotiation.
  • Snapshots-as-manifests makes time travel trivial.
  • Affinity routing is dumb on purpose — easy to reason about.
  • Workers stay stateless; restart at will.
Process
  • Make EXPLAIN beautiful from day one.
  • Round-trip Arrow types end-to-end before adding features.
  • Build the dev_stack.sh first. You'll run it 10,000 times.
  • Type your errors (CATALOG / BINDER / CONSTRAINT) so clients map cleanly.
  • Set explicit gRPC message limits — never trust defaults.
Roadmap · five features on deck

What's next

The first two are foundations. The other three fall out of them — almost for free.

1 · Structured plan IR · the real M3

Beyond SQL strings on the wire

A serialized operator tree replaces SQL on the gateway↔worker boundary. Aggregation push-down and per-operator placement become real rewrites instead of leaky hints.

2 · Materialized views · diff-storage's killer app

REFRESH ON COMMIT

Snapshots are perfect substrate for cheap MVs. Full refresh first, incremental refresh next — cache-coherent by construction because the snapshot id is the cache key.

3 · Read replicas · cache-aware routing

Route reads to the worker that already has them

Each worker reports which snapshots it has cached on heartbeat. Gateway prefers a worker that's already warm — fewer object-store fetches, geo-distributed reads, failover is just a routing decision.

4 · WASM extension · DuckDB in the browser

Browser-side dual execution

Same extension shape, gRPC-Web on the wire, Arrow IPC unchanged. Unlocks the in-browser column explorer / zero-latency interactive UI shape that MotherDuck pioneered.

5 · Forks & zero-copy clones

CREATE DATABASE staging FROM production;

Metadata-only operation. Returns in <100 ms regardless of source size; costs zero bytes. Ref-counted layers prevent GC of shared data. MotherDuck's stickiest feature, ours under MIT.

Dependency edges — 2 · 3 · 5 need differential-storage-end-to-end · 2 · 3 · 4 need the IR. Foundations first; the wins compound.
